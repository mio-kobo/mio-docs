**版本范围：Mio v2.0.0**，标签 `v2.0.0`，提交 `0ce04dd06c6c6e4e26f55a2c0b4ffb23aa942a0a`；CLI 版本 `Mio 2.0.0`。本页描述 Mochi VM 与原生后端共用的字节码格式；Go AOT 与纯 Mio Native AOT 的边界见 [Native AOT](/docs/v2.0/internals/native-aot)。

Mochi 是 Mio 的二进制字节码容器。所有多字节整数使用大端字节序，文件不包含填充、校验和或尾随数据。

Mochi v14 增加受限数据复制转换指令。解码器和 VM 可以读取 Mochi v1 至 v14。`Version = 14` 是实现支持上限；Go 编码器的 `encodedVersion` 按实际常量与指令选择输出版本，并非每次 build 都写 14。含 `OpDataConvert` 的程序写 v14。

## 公共头部和主指令流

| 字段 | 大小 | 说明 |
| --- | ---: | --- |
| 签名 | 5 字节 | ASCII `MOCHI` |
| 版本 | `uint16` | `1` 至 `14` |
| 常量数量 | `uint32` | 后续常量条目数 |
| 常量表 | 可变 | 见下节 |
| 全局槽位数量 | `uint32` | VM 启动时分配的槽位数 |
| 主指令长度 | `uint32` | 指令字节数 |
| 主指令 | 可变 | 编码后的 Opcode 与操作数 |

Mochi v1 在主指令后结束。Mochi v2 至 v14 继续写入函数表。

## 常量表

每个常量以一个 `uint8` 类型标签开始：

| 标签 | 数据 |
| ---: | --- |
| `1` | 一个按位保存的 `int64`，占 8 字节 |
| `2` | `uint32` UTF-8 字节长度，随后是字符串数据 |
| `3` | 一个 IEEE 754 binary64 位模式，占 8 字节，Mochi v3 及后续版本允许 |
| `4` | 一个 IEEE 754 binary32 位模式，占 4 字节，Mochi v10 起允许 |
| `5` / `8` | `int8` / `uint8` 位模式，占 1 字节，Mochi v11 起允许 |
| `6` / `9` | `int16` / `uint16` 位模式，占 2 字节，Mochi v11 起允许 |
| `7` / `10` | `int32` / `uint32` 位模式，占 4 字节，Mochi v11 起允许 |

布尔值和 `mu` 不进入常量表，分别由 `OpTrue`、`OpFalse` 和 `OpNil` 产生。

## Mochi v2 至 v14 函数表

主指令后先写入 `uint32` 函数数量，每个函数依次包含：

| 字段 | 大小 | 说明 |
| --- | ---: | --- |
| FunctionID | `uint16` | 从 0 开始，必须与函数表索引一致 |
| 名称长度 | `uint16` | UTF-8 名称的字节数 |
| 名称 | 可变 | 非空 UTF-8 文本 |
| 参数数量 | `uint32` | 函数参数槽位数 |
| 局部槽位数量 | `uint32` | 包含参数槽位，不能少于参数数量 |
| 标志 | `uint8` | bit 0 表示函数返回值，其余位必须为 0 |
| 捕获数量及捕获项 | 可变 | v9 起：`uint32` 数量，每项为 `uint8` 来源和 `uint32` 索引 |
| 指令长度 | `uint32` | 函数指令字节数 |
| 指令 | 可变 | 独立函数指令流 |

## 验证限制

| 项目 | 上限 |
| --- | ---: |
| 文件 | 64 MiB |
| 常量 | 65,536 |
| 全局槽位 | 65,536 |
| 单个字符串 | 16 MiB |
| 主指令或单个函数指令 | 16 MiB |
| 函数 | 65,536 |
| 函数名称 | 65,535 字节 |
| 单个函数的参数或局部槽位 | 65,536 |

解码器还会检查 UTF-8、索引范围、函数元数据、返回指令种类和跳转边界。文件末尾不允许额外数据。VM 会继续检查运行时类型、Value Stack、局部槽位初始化、调用深度和指令预算。

## 兼容性

- v1 文件没有函数表，只能表达主指令流。
- v2 保留完整的 v1 前缀，并在末尾增加函数表。
- v3 只新增常量标签 `3`，函数表与 v2 一致。v1/v2 解码严格拒绝该标签。
- v4 只新增 Opcode 28 和 29，二进制布局与 v3 一致。v1/v2/v3 解码严格拒绝这两个 Opcode。
- v5 只新增 Opcode 30 和 31，二进制布局与 v4 一致。v1 至 v4 解码严格拒绝这两个 Opcode。
- v6 只新增 Opcode 32 和 33，二进制布局与 v5 一致。v1 至 v5 解码严格拒绝这两个 Opcode。
- v7 只新增 Opcode 34 和 35，二进制布局与 v6 一致。v1 至 v6 解码严格拒绝这两个 Opcode。
- v8 只追加 Opcode 36 至 45，二进制布局与 v7 一致。v1 至 v7 解码严格拒绝这些 Opcode。
- v9 在函数项中加入闭包捕获元数据，并追加 Opcode 46 至 49。
- v10 新增 binary32 常量标签 `4`，并追加 Opcode 50 至 54。旧版本严格拒绝这些标签和指令。
- v11 增加固定宽度整数常量标签与 `OpIntegerConvert`。
- v12 增加 Opcode 56 至 62，用于通用动态数组操作。
- v13 增加 Opcode 63 和 64，用于数组截断与批量追加。
- v14 增加 `OpDataConvert`。当前只允许 `string` 与紧凑 `[]uint8` 的复制转换。
- 不使用新能力的既有程序保持原二进制语义；解码器继续接受合法 v1 至 v13。
- 格式没有校验和或签名。加载不可信文件时必须经过 `mochi.Decode`，不能绕过验证直接执行原始字节。

后续格式若需要不兼容变更，应使用新的版本号，不能改变已有字段或 Opcode 编号。


## 执行系统与验证范围

Go VM 对解码后的字节码运行共享 Value Stack 与调用帧；Mochi 容器不是 ARM64 可执行文件。`build → exec` 可验证序列化后执行行为，`disasm` 列出字节码结构。相关源码为 `internal/mochi/mochi.go`、`validate.go`、`internal/code/code.go` 与 `internal/vm/vm.go`。

本页示例与字节码输出已使用官方 v2.0.0 发行包的 `build` / `exec` / `disasm` 路径验证；Hello 程序的实际 Mochi 输出与 `Constants` / `Instructions` 结构记录在 [CLI](/docs/v2.0/tooling/cli)。更早的完整 fixture 验证记录保留在 `verification/content-quality/`，不能自动改标为本轮对 v2.0.0 的重新执行。完整限制与来源见 [验证与来源](/docs/v2.0/tooling/verification)。

Go VM 的对象生命周期由 Go 宿主管理；Native 精确 GC 是另一个 Runtime，不应混用资源上限或验收结论，见 [GC](/docs/v2.0/internals/gc)。
