## 验证与来源

Mio 的功能与工具链会随着版本变化，因此编写官方文档时，应以明确的源码版本作为依据。

本文档对应 **Mio V2.0.0**。其中，CLI、Mochi、Bunko 和 MioCore LSP 均以该版本的核心源码为基础。编辑器插件属于独立项目，应另行确认插件版本与运行环境。

### 版本基线

| 项目 | 版本或来源 |
| --- | --- |
| Mio 语言版本 | `v2.0.0` |
| 发布标签 | [`v2.0.0`](https://github.com/mio-kobo/mio/releases/tag/v2.0.0) |
| 源码提交 | `0ce04dd06c6c6e4e26f55a2c0b4ffb23aa942a0a` |
| CLI 版本字符串 | `Mio 2.0.0` |
| 字节码系统 | Mochi v14 |
| 官方预编译发行平台 | macOS Apple Silicon ARM64 |
| 标准库来源 | `bunko/kiso/` |
| 语言服务器来源 | `internal/lsp/` |

这里的版本信息用于说明文档的适用范围，不表示其他版本的 CLI、插件或 Native AOT 一定具有相同功能。

### 核心功能验证

对于一个完整的 Mio 程序，可以按照以下顺序检查源码与字节码执行流程。

首先创建 `Hello.mio`：

```mio title="Hello.mio"
chant("Hello, Mio!");
```

随后使用终端执行：

```sh
mio version
mio check Hello.mio
mio run Hello.mio
mio build -o Hello.mochi Hello.mio
mio exec Hello.mochi
mio disasm Hello.mochi
```

`check` 用于确认静态检查能够通过，`run` 用于确认源码运行，`build` 用于生成字节码，`exec` 则用来验证编译产物能够执行。

`disasm` 可用于检查字节码中的常量、指令和函数信息，但其文本格式不应直接视作 Mio 源码的可逆表示。

### 标准库验证

使用 Bunko 时，应确认 CLI 能正确定位标准库目录，并在每个独立的示例文件中添加需要的 `yobu` 导入语句。

例如：

```mio title="Math.mio"
yobu "kiso/math";

kaku value: float64 = 144.0;
chant(math.sqrt(value));
```

可以使用：

```sh
mio check Math.mio
mio run Math.mio
```

如果 Bunko 未安装到项目目录中，可以通过 `MIO_BUNKO` 指定标准库物理根。

### 自动化检查

Mio 文档仓库包含示例检查脚本，可以使用指定的 CLI 和 Bunko 运行可验证的程序样例。

在 `mio-docs` 仓库根目录下，可以根据已配置的文档版本执行：

```sh
DOCS_VERSION=v2.0 \
MIO_CLI="$MIO_HOME/mio" \
MIO_BUNKO="$MIO_HOME/bunko" \
node scripts/check-examples.mjs
```

这个脚本用于检查仓库中它所覆盖的文档示例，并不意味着它会自动发现所有新建的 Markdown 代码块。

新增文档仍应逐个检查示例是否完整、是否依赖外部文件、是否需要只在 `mio test` 下使用的测试环境，以及是否需要不可用的宿主功能。

### 网页 Playground 验证

文档站中的 Playground 依赖浏览器 WASM 运行环境，并不等同于安装在本机的完整 CLI。

当前网页内置的 Bunko 模块仅包含 `kiso/math`、`kiso/array`、`kiso/string`、`kiso/bytes` 和 `kiso/utf8`。

为了让示例尽量可以直接运行，应遵循以下要求：

- 每个可运行的 `mio` 代码块都是完整程序，不依赖同一页面其他代码块的导入或变量。
- 使用标准库时在代码块内部写入完整的 `yobu` 语句。
- 无法在网页独立运行的片段应标注 `no-run`，测试文件还应标注 `mode=test`。
- CLI 命令使用 `sh` 代码块，不作为 Mio 源码运行。
- 故意演示编译错误的 Mio 代码也应标注 `no-run`。

Playground 的自动启用条件由文档仓库中的 `source.config.ts` 和 `components/mio-code-block.tsx` 控制。

### 测试命令验证

对于测试文件，应使用 `mio test` 而不是 `mio run`。

例如：

```mio title="number_test.mio" mode=test no-run
yobu "kiso/testing";

waza test_number() -> unit {
    testing.expect(6 * 7 == 42, "数值计算应当正确");
}
```

在项目中执行：

```sh
mio test .
mio test ./... --format=json
```

除确认退出码以外，还应检查实际运行的测试数量和失败数量。因为没有匹配到任何测试时也可能返回成功退出码。

### 发行平台与运行边界

Mio V2.0.0 的正式预编译发布主要面向 macOS Apple Silicon ARM64。

`mio` 可以完成源码前端和 Mochi VM 工作；`mochi-aot` 与 `native-aot` 负责原生 ARM64 Mach-O 生成。需要区分字节码构建通过、VM 运行通过和 Native AOT 运行通过这三个不同的结论。

编译器与 Native AOT 的支持范围并不完全相同。例如，Native 当前不承诺完整支持 VM 的 Map、任意宿主桥接及全部函数值组合。

官方 V2.0.0 发布包采用 ad-hoc 签名，并未建立 Developer ID 公证和全部 macOS 版本的兼容性承诺。因此，安装成功、字节码执行成功和原生程序首次启动成功应分别验证。

### 编辑器验证边界

VS Code 与 JetBrains 插件的版本独立于核心语言版本。

| 项目 | 需要验证的内容 |
| --- | --- |
| VS Code | 插件能否找到 CLI、启动 MioCore、获得诊断与补全 |
| JetBrains | Mio SDK、Bunko 路径、CLI 诊断与运行配置 |
| LSP | `initialize`、文档同步、诊断、正常 `shutdown` / `exit` |
| 扩展发布 | 插件包版本、目标 IDE 版本和市场发布状态 |

现有核心仓库具有 MioCore LSP 的协议测试，文档仓库也记录了 V2.0.0 的语言服务握手验证。这些记录不能自动证明每个编辑器版本都已通过完整端到端测试。
