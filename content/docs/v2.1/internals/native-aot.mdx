## V2.1 架构演进与核心能力 <FeatureBadge status="updated" since="2.1" /> <PlatformSupport showArch={true} systems={{ macos: { arm64: "full" }, linux: { x86_64: "full" }, windows: { x86_64: "full" } }} />

V2.0 阶段已经验证了 Mochi VM、Go AOT 以及纯 Mio Native AOT 后端（M18 里程碑验证了 **Mochi → 原生程序**的多代自编译）。

在 **v2.1.0** 中，Mio 完成了从“独立后端”到“全链路纯 Mio 原生工具链”的跨越：将纯 Mio 源码前端、Mochi IR（解码上限升级至 v16）、多平台 Native lowering、目标文件生成器（Mach-O / ELF64 / PE32+）以及本地签名收尾整合进统一的 `mio` 命令行工具中。在常规开发与发行构建中，不再依赖外部 Go 编译器或链接器进行中间交接。

### 执行与编译路径对比

| 路径                          | 输入 → 中间件 → 产物                    | 当前定位与验证状态                                                         |
| ----------------------------- | --------------------------------------- | -------------------------------------------------------------------------- |
| **v2.1.0 纯 Mio Native CLI**  | `.mio` → 内存 Mochi IR → 原生可执行文件 | **v2.1.0 正式默认路径**（支持 Darwin ARM64 / Linux AMD64 / Windows AMD64） |
| **V2.0 Go CLI + Mochi VM**    | `.mio` → `.mochi` → VM 执行             | 保留的参考实现与语义差分基准（Web Playground 亦基于 Go Web 参考 VM）       |
| **V2.0 Go AOT / 纯 Mio 后端** | `.mochi` → Darwin ARM64 Mach-O          | M18 历史阶段性成果（详见文末历史附录）                                     |

**核心变更边界：**

- `mio build` 默认直接生成当前宿主平台的原生可执行文件；若需输出字节码，需显式指定 `--emit=mochi`。
- `mio run` 与 `mio exec` 采用原生构建并拉起子进程的启动流程，并支持通过 `--` 分隔并传递通用程序参数（`argv`）。
- 网页端 Playground 运行的是 Go Web 参考 VM，并非浏览器内的原生编译器，不支持宿主文件、原生网络或进程操作。

## v2.1.0 正式 CLI 与工作流

v2.1.0 的正式工具链集成于单一的 `mio` 可执行文件中，提供完整的开发、编译与诊断子命令：

| 命令                                           | v2.1.0 行为说明                                         |
| ---------------------------------------------- | ------------------------------------------------------- |
| `mio check FILE.mio`                           | 执行纯 Mio 静态类型检查与错误报告                       |
| `mio build FILE.mio -o OUT`                    | 默认编译为当前宿主平台的原生可执行文件                  |
| `mio build FILE.mio -o OUT.mochi --emit=mochi` | 显式输出 Mochi 字节码文件（Decoder 上限为 v16）         |
| `mio run FILE.mio -- ARG...`                   | 编译临时原生程序并执行，将 `--` 后的参数透传给目标程序  |
| `mio exec FILE.mochi -- ARG...`                | 将已有 `.mochi` 字节码编译为临时原生程序并执行          |
| `mio test PATH`                                | 启动原生子进程测试运行器，采集 stdout/stderr 与退出状态 |
| `mio lsp`                                      | 启动基于 stdio JSON-RPC 的自托管语言服务器              |
| `mio disasm FILE.mochi`                        | 反汇编 Mochi 字节码                                     |

### 最小可复现示例

准备源码 `Hello.mio`：

```mio
chant("Hello, Mio!");
```

使用 v2.1.0 正式 CLI 执行检查、原生构建、运行与字节码检验：

```sh
# 1. 静态检查与版本确认
mio version
mio check Hello.mio

# 2. 默认原生构建与直接运行
mio build Hello.mio -o Hello-native
./Hello-native
mio run Hello.mio -- arg1 arg2

# 3. 显式导出 Mochi 字节码、反汇编及执行
mio build Hello.mio -o Hello.mochi --emit=mochi
mio disasm Hello.mochi
mio exec Hello.mochi -- arg1 arg2

# 4. 跨平台交叉编译（产物需在对应目标操作系统上运行）
mio build Hello.mio --target=linux-amd64 -o Hello-linux
mio build Hello.mio --target=windows-amd64 -o Hello.exe
```

### 关键选项与库路径解析

- `--target=darwin-arm64|linux-amd64|windows-amd64`：指定原生目标平台，默认值为当前宿主架构。
- `--gc-stress`：开启原生构建的内存安全压力验证模式（仅用于测试验证，非生产默认）。
- `--observe` 与 `--emit-symbols PATH`：内存观测与符号输出，**仅限 Darwin ARM64 源码原生 `build`**，不可与 `--emit=mochi` 混用。
- `--bunko-root DIR`：显式指定 Bunko 标准库根目录。若路径非法将直接报错（如返回 `E_BUNKO_ROOT` 与退出码 `2`），不会静默回退。

**Bunko 库查找优先级：**

1. 命令行显式传入的有效 `--bunko-root`；
2. `MIO_BUNKO` 环境变量；
3. 可执行文件所在目录的相对路径 `../bunko`（迁移 Full 发行包时需保持 `bin/` 与 `bunko/` 的相对层级）；
4. 若以上均未找到，不导入 `kiso/...` 的独立程序仍可正常编译；导入标准库则会报路径缺失错误。

## 目标平台、二进制格式与签名边界

v2.1.0 正式发行矩阵严格限定于以下三个目标三元组。其他架构（如 macOS x86-64、Linux ARM64、Windows ARM64）尚未列入 v2.1.0 正式验收范围：

| 目标三元组      | 指令集  | 二进制格式 | 系统边界与依赖                                                     | 签名与验证要求                                                         |
| --------------- | ------- | ---------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| `darwin-arm64`  | AArch64 | Mach-O     | Darwin 系统入口及平台支持                                          | 工具链自动生成 **ad-hoc 签名**；可用 `codesign --verify --strict` 校验 |
| `linux-amd64`   | x86-64  | 静态 ELF64 | 原生 syscall 路径，**无 libc 依赖**                                | 不适用 Mach-O 签名流程；直接校验 ELF 头与执行权限                      |
| `windows-amd64` | x86-64  | PE32+      | 遵守 Win64 调用约定（16B 对齐 / 32B shadow space）与 KERNEL32 边界 | 不适用 Mach-O 签名流程；校验 PE 头与运行表现                           |

**平台安全与异常边界说明：**

- **macOS 签名限制：** 工具链生成的 ad-hoc 签名仅满足本地结构自洽校验，**不等同于 Apple Developer ID 签名或公证（notarization）**。从互联网下载的产物仍受 Gatekeeper 首次运行限制约束。
- **Windows 异常展开限制：** 部分 Windows 运行时例程未包含完整的 SEH unwind 记录。由于 Mio 语言本身不依赖结构化异常展开（SEH），这主要影响外部调试器的栈回溯与崩溃转储分析，不应视为完整的原生 SEH 支持。

## Runtime ABI (RA-1) 与垃圾回收架构

三个原生目标共同遵循 **RA-1（Runtime ABI v1）** 契约。RA-1 统一的是**程序可见语义与内存安全不变量**（可达对象绝不误回收、标量绝不误判为堆指针、内存耗尽必须产生可观察失败），而非强制不同操作系统使用完全一致的底层对象字节布局。

| 架构维度             | Darwin ARM64 (`generational-v1`)                         | Linux / Windows AMD64 (`x64-marksweep-v1`) |
| -------------------- | -------------------------------------------------------- | ------------------------------------------ |
| **字长与字节序**     | 64 位小端                                                | 64 位小端                                  |
| **对象头与对齐**     | 16 字节对象头 / 16 字节对齐                              | 16 字节对象头 / 8 字节对齐                 |
| **对象移动策略**     | **非移动式（Non-moving）**                               | **非移动式（Non-moving）**                 |
| **回收算法**         | **分代 GC**（Young / Old 代际，支持 Minor / Major 回收） | **单代精确 Mark-Sweep**                    |
| **大对象空间 (LOS)** | 含头及对齐总跨度 ≥ 128 KiB 进入独立映射的 LOS | 分配于常规空闲链表堆块，不设独立 LOS       |
| **栈根定位方式**     | 精确 Shadow Frame                                        | `rbp` 栈帧链 + 调用点内联描述符            |
| **跨代写屏障**       | 必需（通过 Remembered Set 维护 Old → Young 引用）        | 单代架构，无跨代写屏障需求                 |

**GC 与并发设计边界：**

- **单变更器（Single-mutator）模型：** RA-1 默认运行在单线程变更器模型下，仅在安全点（Safe Points）触发垃圾回收。
- **并发 GC 状态（M19）：** 仓库中虽包含 Thread/TLS、Epoch、SATB 及并发 Mark/Sweep 的阶段性源码与子阶段测试，但在 **v2.1.0 正式发行版中并未默认开启**，也尚未通过全局并发总门禁验收。内部压力监控状态（`Normal / Elevated / High / Critical`）属于运行时内部遥测，并非面向用户的 `High / Balanced / Low` 三档配置。
- **性能与跨语言边界：** v2.1.0 专注于语义一致性与内存安全，不提供“任意负载下 GC 停顿上限”或“性能超越 C”的承诺。由于跨平台对象布局不同，严禁直接将原生 GC 堆对象裸露给外部 C/FFI 边界。

## v2.1.0 可信自举链与固定点验证

v2.1.0 的正式发行构建放弃了直接从旧版 Go 工具链临时编译的路线，转而采用基于不可变可信种子（`bootstrap-v2.1.0-seed.1` 中的 `mio-v2.1.0-darwin-arm64`）的多阶段固定点验证体系：

```text
Trusted Seed (mio-v2.1.0-darwin-arm64)  [核验 Tag、SHA-256、GitHub Attestation 与严格签名]
   │
   ▼  (启动新版本源码构建；不要求 Seed 与 Stage A 字节一致)
Stage A (Darwin ARM64)
   │
   ▼  (纯 Mio 源码全链路自编译)
Stage B (Darwin ARM64)  ──┬──► 交叉编译 Linux AMD64 / Windows AMD64 (组 1)
   │                      │
   ▼  (哈希严格一致)       │
Stage C (Darwin ARM64)  ──┼──► 交叉编译 Linux AMD64 / Windows AMD64 (组 2，与组 1 字节一致)
   │                      │
   ▼  (哈希严格一致)       │
Stage D (Darwin ARM64)  ──┴──► 与三平台各自本机原生构建产物进行跨目标 SHA-256 对照
```

- **严谨的固定点定义：** 并非 `A == B == C == D` 四个阶段字节全等，而是同一目标平台下的 **Stage B、Stage C 与 Stage D 完整二进制镜像逐字节（SHA-256）一致**，且 Darwin 交叉编译出的 Linux/Windows 产物与对应平台本机原生构建的产物哈希完全一致。
- **验证边界：** 固定点证明了编译器构建过程的确定性与来源链纯净度，但确定性本身不能单独证明生成的代码不存在逻辑 Bug，因此仍需结合 RA-1 内存压力测试、VM-Native 差分回归以及三平台真机测试共同完成验收。

## 原生支持范围与已知限制

Native 后端与参考 VM 在已覆盖的核心语法与标准库上保持语义一致，但使用时需注意以下工程边界：

- **支持的核⼼路径：** 静态类型与泛型实例化、数组（含 nullable）、结构体、枚举、闭包与共享捕获 Cell、间接函数调用、大对象分配以及 NativeFS 文件操作。
- **宿主与网络边界：** Windows 平台的 `kiso/net/tcp` 在 v2.1.0 中公开支持的是**阻塞式 IPv4（基于 Winsock）**，不应外推为支持 UDP、DNS、IPv6 或 TLS。
- **平台细微差异：** x86-64 原生输出与 Darwin 在极少数格式化路径上存在差异（例如直接对浮点数调用 `chant(float)`），建议优先使用标准库中受支持的 `convert.format_float64` / `format_float32` 函数。
- **错误诊断行为：** 某些底层原生运行时错误（如边界异常或内存耗尽）可能直接触发进程异常退出，而不保证在 `stderr` 输出完整的格式化文本。编写自动化测试时，应综合断言进程退出码、`stdout`/`stderr` 以及预期副作用，切勿仅依赖退出码 `0` 或单一日志行判定成功。

## 发行包交付形态

v2.1.0 为三个正式平台分别提供 `Core` 与 `Full` 两种归档包（同一平台下两者的 `mio` 编译器二进制 SHA-256 完全一致）：

| 平台              | Core 正式包（仅编译器）              | Full 正式包（含 `bunko/kiso/` 标准库与示例） |
| ----------------- | ------------------------------------ | -------------------------------------------- |
| **macOS ARM64**   | `mio-2.1.0-darwin-arm64-core.tar.gz` | `mio-2.1.0-darwin-arm64-full.tar.gz`         |
| **Linux AMD64**   | `mio-2.1.0-linux-amd64-core.tar.gz`  | `mio-2.1.0-linux-amd64-full.tar.gz`          |
| **Windows AMD64** | `mio-2.1.0-windows-amd64-core.zip`   | `mio-2.1.0-windows-amd64-full.zip`           |

- **Core 包：** 包含核心 `mio` 可执行文件（已内置 `check`、`build`、`run`、`exec`、`test`、`lsp`、`disasm` 全部子命令），适合构建不依赖 `bunko/kiso/` 的独立项目。
- **Full 包：** 额外附带独立的 `bunko/kiso/` 标准库源码树、已验证示例及发行元数据。此外，v2.1.0 额外提供 Windows 安装器以及 Linux AMD64 Full 离线 Docker 镜像归档。

## 历史附录：V2.0.0 与 M18 阶段实现（已归档）

> **注意：** 以下内容仅记录 **V2.0.0 时期（M18 里程碑）** 的工具链形态与验证历史。自 v2.1.0 起，用户应统一使用上文所述的正式 `mio` CLI，以下旧工具协议仅作为历史档案与内部开发参考保留。

### 1. V2.0.0 的三条独立执行路径

在 V2.0.0 中，源码前端与 VM 仍由 Go 实现，原生编译仅支持 **Darwin ARM64** 且默认构建不输出原生文件：

- **Mochi VM（V2.0 默认）：** `mio build` 仅生成 `.mochi`（最高 v14），`mio run` 通过 Go VM 解释执行。
- **Go AOT (`mochi-aot`)：** 独立的 Go 命令行工具，将 `.mochi` 编译为未签名的 Darwin ARM64 Mach-O（支持 `-heap-mib 1..1024`、`-gc-stress` 等 Go `flag` 选项，不支持通用程序 `argv`）。
- **纯 Mio Native AOT (`native-aot`)：** M18 Stage 4 生成的早期纯 Mio 编译器二进制，无常规 CLI 参数，也不支持通用 `argv`。

### 2. M18 历史自编译来源链（Mochi → Native）

M18 验证的是后端脱离 Go 的能力，而非全源码工具链自举：

```text
Go 源码前端 → native-aot.mochi (Mochi v14)
Go AOT(native-aot.mochi) → Seed          # 唯一一次由 Go AOT 生成
Seed(native-aot.mochi) → Native Stage 1  # 此后在 Darwin ARM64 上由纯 Mio 后端执行
Native Stage 1 → Stage 2 → Stage 3 → Stage 4 → Stage 5 (生成与签名见证)
```

- Stage 1 至 Stage 5 的**未签名 Mach-O 完整字节完全一致**（托管堆协议为 1 GiB；在 256 MiB 受限堆下触发 `gc_count=1` 仍保持字节一致；128 MiB 试验曾发生 OOM）。
- 进程在 `sandbox-exec`（禁用 `process-fork`/`process-exec`、清空 `PATH`）下完成验证。

### 3. M18 早期 `native-aot` 配置文件协议

早期 `native-aot` 二进制通过在当前工作目录读取两个无末尾换行的 UTF-8 文本文件（`input.config` 与 `output.config`）来指定路径，且产物需手动 `chmod +x` 并执行 `codesign`：

```sh
# V2.0/M18 历史用法示例（v2.1.0 用户请勿使用）
printf '%s' "$PWD/hello.mochi" > input.config
printf '%s' "$PWD/hello-pure-native" > output.config
"$MIO_HOME/native-aot" > native-build.log
grep '^native-aot: ok$' native-build.log
chmod +x hello-pure-native
codesign --force --sign - hello-pure-native
```

_该历史工具在部分失败分支（如 `native-aot: decode failed`、`lowering failed`）下仍可能返回退出码 `0`，因此当时必须依赖解析 stdout 首行的 `native-aot: ok` 标记。_
